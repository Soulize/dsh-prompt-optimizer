# DSH 0.7.8 任务意图稳定性与模型表现计划

状态：分析计划，待实施。
基线：v0.7.6；会话级档位与首条模型路由修复待验证后再发布。

## 1. 北极星目标

让工作模型始终处在正确的模型、正确的会话、正确的轮次和正确的上下文中，把能力用于任务本身，而不是被路由错误、历史污染、协议噪声或错误自主边界消耗。

本项目的本质已不是传统提示词优化器，而是位于用户原话与工作模型之间的会话级任务意图编译层：原话保持不变，提取意图、事实、约束、未决项和建议，再编译成可消费且可验证的上下文。

## 2. 四个既定突破点

### 2.1 完成会话级档位

全局默认加会话覆盖。A 可 Heavy，B 可 Off，未覆盖项回落全局。assist、detail、budget、tier 属于会话档位；Bash 等机器级能力保持全局。必须验证重启持久化、A/B 隔离、关闭会话不注入、旧配置无覆盖时兼容。

### 2.2 修正首条消息模型路由

agentDefaultModel 的真实方法是 currentSelection()。旧调用导致新会话首条消息掉到模型清单第一条。路由顺序：会话明确选择、会话已观测模型、宿主 currentSelection；无法确认时不得静默使用清单第一条，应显示 route-unresolved 或跳过优化。

### 2.3 Skill 去重升级为事务绑定

15 秒时间窗只能是最后兜底。优化包绑定 sessionId、messageId、turnId、invocationId；同一事务只允许一次解释、一次提交、一次注入，覆盖重试、并发 Skill、快速连续发送。

### 2.4 上下文从长度截取升级为相关性编译

当前原文完整保留；当前 Skill 只保留相关部分；最近历史优先；更早历史摘要或按相关性选择；工具和项目文件按引用与任务相关性筛选；被压缩或未读取内容必须明确标记。

## 3. 更本质的潜在突破

### 3.1 任务状态机

将任务表示为 received、interpreted、awaiting-decision、executing、verifying、completed 或 blocked。它能减少长任务的重复规划、方向漂移和已解决问题复问；只描述状态和边界，不替工作模型执行全部项目管理。

### 3.2 严格 Intent IR

建立版本化中间表示，包含 sessionId、turnId、messageId、requirements、constraints、observedFacts、unknowns、userDecisions、reversibleDefaults、acceptanceCriteria、sourceRefs 和 operationMode。注入前校验来源、会话、轮次和包版本。

### 3.3 执行反馈闭环

从意图到执行、观察结果、对照验收条件，再只修正偏差。反馈优先使用真实工具结果、测试结果和用户纠正，禁止凭空生成已完成结论。

### 3.4 任务自适应策略

短问题少量约束；多文件任务强调边界、验收和回滚；视觉任务强调可验证产物与用户确认；长文本强调摘要与引用；高风险操作降低自动决策。不是所有请求都无条件使用更强、更慢的优化。

### 3.5 可测的模型表现基准

建立固定任务集，记录首次可用率、改口次数、高影响误决率、工具成功率、重复规划率、方向漂移、返工、token、延迟和失败率。只有质量收益超过成本时才进入默认路径。

## 4. 单轮表现：第一次就把事做对

### 4.1 为什么单轮是独立的杠杆

多轮机制解决的是后续不漂移；单轮决定的是第一次交付的水平。用户看到的对比效果几乎全部来自单轮：模型在没有任何反馈的一次机会里，是否理解了什么算做好，是否在第一个结构性选择上做对了。

单轮上限近似为：第一次交付质量 等于 对什么算做好的理解精度 乘 第一次结构性选择的正确率 乘 可用于实现的注意力预算。

三者都不是靠加长上下文提升的。冗余上下文会同时压低第二项与第三项，所以单轮优化必须以高密度、可执行、无冗余为前提。

### 4.2 质量词的工程化翻译

极其精细、真实、帅气、炫技写真这类词没有工程内容，但决定验收。单轮最直接的提升是把它们翻译成可观察、可自检的维度，而不是零件清单。

原则：每个质量词给二到三个肉眼可判断的观察维度，并给一条最低可接受线。例如：

- 精细：近距观察下主体结构可辨识、比例协调、有细节层次；
- 真实：材质差异、光照方向一致、有接触阴影、无明显穿模；
- 帅气：构图与视角有取舍，主体突出；
- 炫技：至少一处肉眼可见的技术亮点，不是只存在于代码里的亮点。

验收：质量词被翻译成观察维度而非零件数量；删除该翻译后，一次交付的质量确实下降。

### 4.3 首轮架构分叉的显性化

单轮失败多数不是细节没做对，而是在开头很短的时间里默默做了一个结构性选择，然后被锁死。例如单文件 3D 任务：CDN 还是内联、程序化几何还是单一网格、精度与帧率如何取舍、交互如何组织。

优化层在信息足够时应点出本轮的结构性分叉、推荐选择、理由、以及如何替换；信息不足时至少点出分叉本身，让工作模型自己决定。

### 4.4 验收前置与一轮内自检

反馈闭环属于多轮机制；单轮能做的是把验收条件提前放进上下文，并要求工作模型在声明完成前自检：

- 用户明确要求是否全部满足；
- 未决项是否被擅自决定；
- 已知失败模式是否已规避；
- 交付物形状是否符合要求。

这是预置验收，不是替用户验收。检查项必须标明是检查项，不是新增要求。

### 4.5 任务类知识库（单轮最可积累的资产）

同一类任务会反复出现：单文件可视化程序、改一个模块、长文摘要、数据清洗等。每一类都有稳定的结构性分叉、常见失败模式、验收维度和最小可用骨架。

把这些沉淀成按任务类触发的小型 playbook，是单轮提升性价比最高的方向：一次积累，此后每次首轮都受益。

必须守住的边界（0.7.1 的教训）：

- 按任务类触发，不按单个案例生成全局规则；
- 只写会改变决策的内容，不写通用正确话；
- 有可测收益才保留，无收益就删；
- 不把 playbook 变成第二套系统提示词。

### 4.6 一轮做不到时的诚实识别

当任务规模明显超过一次交付能力时，最优的单轮行为不是浅做一遍，而是交付一个可用的第一版并明确后续。优化层应识别这种情况并写进上下文，避免用户拿到看起来完成、实际不可用的结果。

### 4.7 与多轮的关系

单轮与多轮是同一条链条的两端：单轮负责第一次就理解对、选择对、自检对；多轮负责状态不漂移、身份不混淆、反馈能修正。两者共用同一份意图结构与来源约束，区别只在注入时机与内容密度。

## 5. 实施优先级

### P0：先修正确性（不做就没有意义）

- 会话级档位的重启验证与 A/B 隔离；
- 首条消息模型路由；
- 未解析路由禁止静默使用模型清单第一条；
- Skill 的会话、消息、轮次、调用绑定；
- 注入可观测性：把会话、轮次、路由、包来源记进台账。

### P1：单轮提升（第一次就把事做对）

- 质量词的观察维度翻译；
- 首轮结构性分叉的显性化；
- 验收前置与一轮内自检清单；
- 任务类 playbook 的第一批（先做一两类真实高频任务，不铺开）。

### P2：多轮提升（不漂移、可修正）

- 任务状态机；
- 严格 Intent IR；
- 上下文相关性编译；
- 执行到观察再到验收的反馈闭环。

### P3：需要真实样本后才有资格做

- 任务自适应策略；
- 模型表现基准与 A/B 对照；
- 一轮做不到时的诚实识别阈值。

排序理由：先保证身份与路由正确，再提升第一次交付，最后处理长任务连续性。任何一项在缺少可测收益时都不进入默认路径。

## 6. 明确不做

不靠继续加长系统提示词制造高级感；不把所有历史全文塞入模型；不让模型清单第一条成为正常兜底；不把自然语言补丁当不可验证协议；不把 Heavy 变成无限自主；不把用户未确认的质量词升级成硬要求；不凭单个案例增加全局硬规则。

## 7. 总判断

还有突破，而且最本质的突破不是更会写提示词，而是让模型处在身份正确、上下文相关、状态清楚、来源可追溯、结果可反馈的任务环境里。有效表现近似为：模型能力 乘 路由正确 乘 上下文相关 乘 约束质量 乘 工具可用 乘 反馈闭环。

在这条链条上，单轮与多轮各自对应不同的乘数：

- 单轮对应理解精度、首次结构性选择、注意力预算、任务类知识；
- 多轮对应状态连续、身份不混淆、反馈修正、旧包不复活。

两者的共性是：都不靠堆长度，而靠把该给的信息给准、把不该给的信息拿掉。

0.7.8 的成功标准不是输出更多，而是同一任务在不同会话、轮次、模型和失败路径下，都保持一致、可解释、可恢复的执行质量；并且在单轮场景下，第一次交付就明显更接近用户心中的验收标准。

## 附录 A · 交互框架（Interaction Framing）—— 已实现

### A.1 起因（用户实测，2026-09-27）

把同样的要求用口语、带情绪、带关系感的说法讲出来，模型首轮交付明显好于同等字数、同等信息量的正式说法。
用户的关键反证是：**同样字数的正式"高级"提示词做不到那个效果** ⇒ 起作用的不是信息量，而是**语域本身**。

### A.2 机制（不是玄学，是分布）

模型不是被"激励"，而是对提示词的**语域**条件化采样：

- 正式语域 → "专业助手接正式请求"那一簇：客套、hedging、模板化、求稳；
- 口语 + 高唤醒语域 → "哥们帮你把活干出来"那一簇：直接开干、投入、把成品拿出来。

RLHF 数据里真实用户的口语请求占绝对大头，且"要求高、催得急"往往对应被标注更满意的回答；
而正式提示词更像评测题，模型会求稳。口水话里还夹带了真实语义（"硬邦邦"是视觉标准、
"给别人看"是展示场景与受众），并放松了"礼貌助手"人设对预算与承诺度的挤压。

**为什么"妈妈"版弱于"硬邦邦"版**：暖语域移向陪伴/迎合簇，提升舒适度而非执行力，还附带过度赞同的风险；
硬语域移向行动/交付簇，直接命中"一次产出可展示交付物"这类任务。

### A.3 设计决定

- 两档：`framing: neutral | hard`，**全局默认 + 按会话覆盖**，与优化档位**正交**（可以"轻度 + 硬邦邦"）；
- **保留语域**：把 hard 块消毒成正式条目（例如"请更积极主动"）等于扔掉效果来源——正式条目仍采样"专业助手"簇；
- 只作用于工作模型的执行姿态；解释层保持中性（结构化提取不该被语域影响）；
- 三条硬边界：① 自带"插件所加、不是用户的新要求"标签；② **块内显式反制越权**
  （"用户没拍板的大事不准替他定"——强结果导向最大的副作用就是懒得问、自己定了）；③ 不改用户原话；
- 位置：包的最前（先入为主设定语域）；没有其它内容时不单独出现（避免"只有口号没有内容"）。

### A.4 待做的验证（四臂 A/B，必须做）

| 臂 | 内容 | 回答的问题 |
|---|---|---|
| A | 无框架 | 基线 |
| B | 正式化的"强结果导向"条目 | 语义够不够 |
| C | **硬语域块**（已实现） | **语域是不是有效成分** |
| D | 用户原话完整"硬邦邦改写" | 上限参照 |

判读：`C ≈ D > B` ⇒ 语域有效，这一档站得住；`B ≈ C` ⇒ 语义就够，硬档应降级为口味偏好，不该宣称提升表现。
