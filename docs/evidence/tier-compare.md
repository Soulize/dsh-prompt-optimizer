## 关键判断

- 目标：把模糊请求（改页面外观、加动画、修数据）转化为可核验的三项工作，并在信息不足时先查证、后动手。
- 成功标准：① 澄清清单中已确认项能一一对应到实际改动；② 数据问题有复现路径且修复后可验证；③ 视觉与动画改动有对照依据且小步可回退；④ 回归结果不劣于基线；⑤ 交付说明中明确区分"已做"与"未做"。
- 约束：先查证再改；先功能后表现；最小改动；不新增依赖；失败即回退；只读探查期间不得改码；不得虚构页面、症状、技术栈、文件名等用户未提供的事实。
- 未知项：哪个页面；"好看"的参照标准；"数据那块"的确切所指与症状；技术栈与验证命令；是否有设计规范或令牌；动画的作用点与性能预算；用户是否愿意先回答澄清问题。

## 执行计划

- 阶段 0：定位与澄清——只读探查项目结构、候选页面、数据相关模块，向用户提交最小澄清清单，产出"已确认/待确认/未知"三类清单。
- 阶段 1：基线固化与可回退准备——记录分支与工作区状态、构建与测试现状，建立隔离分支，确认本地验证方式。
- 阶段 2：先修数据——复现症状、定位根因、最小修改、可验证通过，产出根因说明与最小 diff。
- 阶段 3：视觉优化——对照参照物列具体改动项，复用既有设计令牌，逐项小步提交。
- 阶段 4：动画——确认作用点与时长，优先合成层属性，处理 reduced-motion 与清理逻辑。
- 阶段 5：回归与交付——验证不劣于基线，输出变更摘要、验收指引与未做事项。

## 多情况预案

- 情况：用户未回答或无法回答澄清问题（说不清是哪个页面 / 数据症状描述不了）。 → 应对：不猜、不改。把候选清单和澄清问题原样再抛一次，并说明"选定后我可在 X 分钟内完成阶段 1–2"；如用户要求"你先看着办"，则只做只读诊断 + 出一份改动提案，不落代码。
- 情况：数据问题无法复现，或复现后行为与描述不符。 → 应对：停止修改，回报"在 Y 环境下按 Z 步骤未复现"，请求提供报错原文、复现环境（本地/预发/生产）、数据样本或截图，并说明需要哪一项才能继续。
- 情况：视觉改动触及全局样式，或与项目既有设计规范/其他页面不一致。 → 应对：回退该改动，收敛到既有令牌与组件范围内重做；若确实需要全局变更，先单独提出方案并等用户确认。
- 情况：动画导致掉帧、布局抖动、可交互时间变差，或 diff 蔓延到未授权文件。 → 应对：立即回退该动画或该批文件，降级为不触发布局的简单过渡，并把超范围改动拆到独立分支再向用户说明——不夹带提交。

## 功能性指令建议

- 建议：**使用 todo 列表 + 计划模式（plan mode）**，不建议用 goal 类目标指令。理由：任务是跨阶段、跨文件、含回退分支的多步作业，需可见进度与逐阶段确认；而在"页面/症状"未确认前，设定一个抽象的 goal 只会诱导下游 AI 自行补全用户没说的内容并直接动手，与"先查证再改"纪律冲突。
- 可直接粘贴的指令句：
  - 「先进入计划模式：只做只读探查，输出"已确认事实 / 待确认假设 / 未知项"清单与分阶段计划，等我确认后再开始改代码。」
  - 「把上述阶段 0–5 建立为 todo 列表，每完成一项更新状态；进入下一阶段前先汇报上一阶段的产出与验证结果。」
  - 「每阶段开始时先复述本阶段的动作与纪律，结束时报出该阶段 diff 的文件清单；任何阶段失败即回退到该阶段起点并停下等我决定。」
