# v0.4.6-beta.4 — 下游形态投影：同一份档位定义，两种消费形态

作者：啃轮胎的西狐 · 2026/09/18

## 本质

**PTC 惩罚的是工序，不是深度。** PTC 执行体用一个程序组合多步、每次往返都要重新起程序，它怕的是"分阶段停下 / 逐阶段汇报 / 先建 goal·todo"这类**节奏要求**；而"细到改哪个文件的哪个函数"对它是**收益**。原先这两件事被写在同一个字段 `decompose: 'exhaustive'` 里，于是"让极端档更适配 PTC"看起来像"必须削掉极端档"——**拆开就不必削**。

## 做法（阶段一 + 阶段二）

1. **拆轴**：档位改由五轴描述——`grounding` / `depth` / `enrich` + **`sequence`（工序 ↔ 清单）** / **`budget`（不设限 ↔ 够用即止）**。前三个是能力定义，后两个是表达方式。
2. **形态投影**：`delivery = ptc` **只**把 `sequence→unordered`、`budget→single-pass`；**不变式：绝不动 depth / enrich / grounding**。档位正文由 `renderV6TierText(tier, axes)` 渲染，全仓只有这一处写"步骤 / 阶段 / 长度"。
3. **运行时判定**：手动覆盖 → 会话 `header.agentPreset` → 回落 `chat`；只读诊断路由 `/delivery` 回报"判成了什么、依据是什么"。UI 新增一行「下游执行体：自动 / 对话式 / PTC」。
4. **消费形态声明块**：`ptc` 时注入一个与 `observerBlock` 同构的结构参数，**只声明读者是谁**，规则本身由轴渲染写一次。

## 实测（同批 10 题、同档 extreme、无工具、两次独立采样）

| 采样 | 形态 | 真实字数 | 流程开销/条 | 逐步/条 | 单程序/条 | 验收/条 | PTC 分 |
|---|---|---|---|---|---|---|---|
| 同批配对 | chat | 5143 | 0.4 | 0.4 | 1.1 | 0.5 | 3.6 |
| 同批配对 | **ptc** | 3711 | **0.1** | **0** | 1.9 | **4.5** | 9.9 |
| 复测 | **ptc** | 4179 | **0** | 0.2 | 0.4 | **5.7** | 6.12 |
| 改前基线 | chat | 3381 | 0.2 | 0 | 0.9 | 0.7 | 6.93 |

**稳健的**：流程开销与逐步**必然更低**（ptc 0.1 / 0，chat 0.4 / 0.2 / 0.2）；验收判据**必然更高**（ptc 4.5 / 5.7，chat 0.5 / 0.7；该指标噪声 sd 仅 0.75，差距 6–8 倍）；**同批配对 8/10 题变好**（均值 +5.8）。

**不稳健、因此不作为结论**：综合 PTC 分与字数——该量尺跨批噪声大于效应（同一 chat 提示词两批之间条目数 sd = 9.85、综合分 ±3.2），ptc 9.9 / 6.12 与 chat 3.6 / 6.93 **区间重叠**。

**档位次序在投影后仍成立**（`tier-ordering.json`，ptc 形态内各 n=10）：条目数 极端 **31.6** > 高级 **22.3** > 普通 **18.3**；字数 3711 / 2438 / 1160。

**零回归**：`delivery=chat` 时三档 system 与改前**逐字节相同**（15/15）。零回归不靠分数证明，靠这条结构事实。

## 顺带修的缺陷

产出预算改为**单一来源 + 停顿看门狗**：硬上限 240s（绝对兜底）+ **45s 无增量才收手**（`DSH_PO_STALL_MS`）。
原先按总时长 60s 一刀切，砍的是**还在稳定产出**的健康请求 → 半截命令。改后 **累计 42 次运行 0 中断**，其中一题跑到 10929 字 / 127 秒正常完成。

## 一处判据更正（如实记录）

初版判据写"条目数与位置引用 ptc ≥ chat"，**不达标**（41.3→31.6 / 4.2→2.7）。复核确认**判据本身写错**：① 噪声就有这么大；② `single-pass` 的目的就是减篇幅，要求条目不减等于要求篇幅不减；③ 该看的是每条目的具体度（0.13→0.11，噪声内）与可验收性（0.5→4.5）。"定义不丢失"改用**档位次序**判定。
