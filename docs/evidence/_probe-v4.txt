在你的工作目录（用户的项目根目录）里执行以下任务。遇到歧义按本命令里的「采用解读」继续，不要反问、不要停下来等确认。

一、目标与判据

目标：在真实运行环境中，坦克的履带部件可见——即渲染坦克的那个页面/场景，在真实浏览器或真实运行程序里打开后，履带出现在画面上，且位置与车体正确贴合（不悬空、不穿插、不埋进地面）。

成功长什么样：在真实媒介里打开渲染坦克的页面/程序，截图中坦克的履带出现在车体两侧下部（或该坦克设计对应的位置），轮廓/贴图可辨识；刷新后仍可见；Console 无新增报错。把修复后的截图与改动前的基线截图并排，差异肉眼可见——履带那一块从"没有"变成"有"。

失败长什么样：
- 页面/程序打开后连坦克车体都不出现 → 属于"跑不起来"，先解决，不算修履带。
- 车体可见，但履带区域仍是空缺、透明、纯黑块、错位、埋进地面，或只在某一种窗口尺寸/浏览器里可见。
- 截图里履带可见，但刷新后、旋转相机后、或动画播放中消失。
- 履带出现的同时，车体或背景被改动（与基线截图产生除履带外的可见差异）。

主观词翻译：
- "显示不出来" → 翻成可观测判据：在真实媒介截图中，履带应占的像素区域与基线一致地不存在/不可辨识。判定方式：与基线截图对比，该区域出现可辨识的履带形状或贴图。
- "修一下" → 翻成约束：改动只限与履带显示直接相关的文件（履带节点定义、履带引用的资源路径、履带材质/坐标/可见性/层级参数）。不做重构、不改车体、不动构建配置与依赖版本。

采用解读：本次只把"履带在真实媒介里可见且位置正确"当作完成；不评判履带造型是否精致、不增加履带细节、不修改坦克其它部分。理由：用户只说了"显示不出来"，没有提外观要求。

二、观测点与基线

媒介与打开方式：在项目里定位渲染坦克的入口（HTML 页面 / 启动脚本 / 场景文件）。用真实浏览器打开——优先项目自带 dev server 的地址；若没有 dev server，直接用 `file://` 打开对应 HTML；若项目需要构建，先按 README / package.json 里已有的脚本跑起来。打开 DevTools 的 Console 与 Network 面板，并对画面截图。

基线：动手改任何文件之前，先在上述真实媒介里打开并截图保存为 baseline（例如存到 `/tmp/baseline.png` 或项目内临时目录），同时记录 Console 报错原文与 Network 面板里所有 4xx/5xx 请求。这张基线是后续所有"是否修好"的唯一对照。

定位具体是哪一个坦克：在项目根目录（排除 node_modules、.git；若 dist 是实际运行产物则不排除）执行大小写不敏感搜索：
`rg -in --hidden -g '!node_modules' -g '!.git' 'tank|坦克|track|履带|caterpillar'`
列出所有命中文件。确认标准：找到至少一个文件，它在真实媒介中打开后渲染出一辆坦克，并且该画面里履带不可见（与基线一致）。这个文件就是本次的观测点，把它的路径写进回执。若命中多个候选，全部打开截图，选"确实有坦克且确实缺履带"的那一个，其余只记录不改。

三、步骤（风险优先：最致命且最便宜的检查排最前）

1. 动作：在真实媒介打开候选页面，确认能跑起来并看到坦克车体。｜预期：页面加载后画面里出现坦克车体（截图可见），Console 无导致中断的报错。｜若不符：先解决"跑不起来"——看 Console 第一条报错、Network 失败项；换启动方式（dev server ↔ 直接开 HTML）、换端口、换有头/无头浏览器重试；把试过的命令与报错原文记下。此步不过，后面都不做。

2. 动作：在基线截图上确认"履带该出现的位置"在哪里，用车体做参照（履带通常贴在车体两侧下部或底部）。｜预期：能指出一个具体区域，该区域现在没有履带。｜若不符：若车体也没有，回到第 1 步；若无法判断履带位置，读模型/场景文件里履带节点的坐标与父节点，或临时给履带节点加高饱和高亮色（诊断用，交付前删除）后截图，靠颜色定位它该在的位置。

3. 动作：分层排查履带为什么不可见。按下面顺序，每一步都在真实媒介复观测，只前进一步就停：
   a. 该在的东西在不在：读场景/模型文件，确认履带节点（mesh / group / sprite / DOM 元素）确实被创建并挂到坦克上。｜预期：找到履带节点，且其 visible/enabled 为真、未被父级隐藏。｜若不符：记录节点不存在或被隐藏，改法只针对这一处。
   b. 资源在不在：看 Network 面板，履带用到的模型/贴图/材质文件请求是否成功（200）。｜预期：无 404/5xx，且响应体非空。｜若不符：拿到失败 URL，按项目现有资源路径规则修正路径或补齐资源（只补履带所需，不引入新素材风格）。
   c. 渲染层是否被遮/剔除：临时把车体隐藏（诊断用）只留履带，截图。｜预期：履带单独出现。｜若仍不出现，问题在履带自身（材质/坐标/缩放/相机视锥）；若单独出现、合起来不出现，问题在层级/遮挡/深度（z-fighting、depthTest、renderOrder、透明排序），只改这些相关参数。
   d. 尺寸/位置：读履带节点相对车体的坐标与 scale，和车体包围盒比对。｜预期：履带位于车体两侧下部，尺寸与车体成比例。｜若不符：只调履带的 position/scale，不动车体。
   e. 相机/视锥：确认履带在相机可见范围内（相机 near/far、frustumCulled）。｜预期：履带包围盒与相机视锥相交。｜若不符：只改履带的 frustumCulled 或相关相机参数中最小必要项，并在回执里说明改了什么。

4. 动作：实施修复（只改与履带显示直接相关的那一处/几处）。｜预期：保存后重新打开真实媒介，履带可见，Console 无新增报错。｜若不符：回退到上一步观测点，换第 3 步里未试的下一个假设（a–e），不要叠加多处改动。

5. 动作：修完回到同一观测点复观测，与 baseline 对比。｜预期：新截图里履带区域出现可辨识的履带；车体、背景、其它部件与 baseline 一致（除履带外无可见差异）。｜若不符：若履带出现但车体被改坏 → 回退车体相关改动；若履带仍不出现 → 记录为 fail，附上截图与 Console 原文，进"未验证清单"。

6. 动作：删除所有临时诊断代码、高亮色、临时文件。｜预期：`git status` 或文件比对只显示与履带显示直接相关的改动。｜若不符：逐项还原，直到 diff 只含必要修改。

四、探针清单

1. 问题：不知道这个项目里"坦克"具体在哪个文件、什么技术栈渲染。｜最小实验：根目录 rg 搜索 + 逐个打开候选页面截图。｜什么结果算失败：搜不到任何命中，或所有候选页面里都没有坦克。｜失败时改走：扩大搜索关键词（vehicle、panzer、armor、model、gltf、three、canvas、sprite）；仍无 → 报告"未找到坦克渲染入口"，判 fail，不猜着改。

2. 问题：不确定履带是独立资源（模型/贴图）还是代码生成（几何/形状/DOM）。｜最小实验：读履带节点定义处，看它引用了什么；若是外部 URL，用 DevTools Network 看该 URL 状态码。｜什么结果算失败：URL 404 或响应 0 字节。｜失败时改走：按项目已有资源目录结构修正路径；若资源确实不存在，报告"资源缺失"，不擅自生成新素材（除非项目里已有同类履带资源可直接复用）。

3. 问题：不确定是"没渲染"还是"渲染了但和背景/车体同色看不出"。｜最小实验：临时把履带材质改成高饱和荧光色（诊断用）后截图。｜什么结果算失败：改了颜色仍看不见任何形状。｜失败时改走：属于几何/坐标/视锥问题，转第 3 步 c/d/e。

4. 问题：不确定是否只在特定窗口尺寸/浏览器/无头模式下丢失。｜最小实验：同一页面用两种方式各开一次（例如有头 Chrome 与无头截图），窗口尺寸分别为默认与 375×812。｜什么结果算失败：一种可见另一种不可见。｜失败时改走：按最保守处理，修到两种都可见；若无法同时满足，在回执里写明差异，判 fail 并进未验证清单。

5. 问题：不确定改动是否破坏了车体或其它场景元素。｜最小实验：修后截图与 baseline 逐区域对比（车体、背景、UI 元素）。｜什么结果算失败：出现除履带外的可见差异。｜失败时改走：回退该改动，换更局部的改法（例如只改材质参数而非重建节点）。

五、隐含要求（只加检查与约束，不加工作量）

- 不碰：坦克车体几何/贴图、相机默认视角以外的场景元素、UI、构建配置、依赖版本、与履带无关的任何文件。
- 回归：修复前后同一观测点截图对比，除履带外无可见差异；Console 无新增报错。
- 边界输入：默认窗口尺寸与 375×812 两种尺寸；刷新后；相机旋转/缩放后；动画播放中（若有）履带均可见。
- 兼容性：若项目声明支持多浏览器，至少在 Chrome 真实浏览器里验证；无头模式只能作为辅助定位手段，不能单独作为"完成"的判定依据。
- 采用解读：本次不做"让履带更好看/更真实"，只保证履带可见且位置正确。理由：用户只说"显示不出来"。
- 采用解读：若定位发现同时有多辆坦克/多个页面缺履带，只修基线截图对应的那一个，其余只记录在回执里。
- 手段：允许装项目已有依赖、跑构建、写临时诊断代码；临时物交付前必须删除。关键判定不得硬编码为成功；任何验证方式必须先用一个已知坏样本证明它会报错。

六、交付物与回执

产物：修改后的相关文件（列出完整路径）+ 修改后的 diff（`git diff` 原文）。若只是配置/路径修正，产物即该文件。

证据（必须来自真实浏览器/真实运行环境，不接受"我读代码确认没问题"）：
- baseline 截图路径（改动前真实媒介截图）
- 修复后同观测点截图路径（真实媒介截图）
- Console 面板原文（含任何报错/警告）
- Network 面板里履带相关请求的状态码原文
- 运行/启动命令原文

回执：逐条对照"一、目标与判据"写 pass / fail；每个 fail 写清差在哪（截图里看不到什么、报错原文是什么）。

未验证清单：哪些项没能在真实媒介里确认（例如"项目声明的 Firefox 未安装，未验证"）。没有就写"无"。
